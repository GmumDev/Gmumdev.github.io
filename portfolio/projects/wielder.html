Wielder

4인 멀티플레이 보스런 · 팀 4인 (팀장) · 2026.06 – 09 · Unity 6 · Photon Fusion 2

3D 타일 쿼터뷰의 4인 협동 보스런입니다. 팀 전원이 Photon Fusion 2를 처음 쓰고, 팀원마다 쓰는 AI 도구가 달랐습니다. 저는 팀장으로서 코드를 쓰기 전에 모듈 경계 · 네트워크 규칙 · 문서 동기화를 정적 검사로 강제하는 가드레일을 만들었고, 그 위에서 네트워크 토대와 초기 무기 시스템, 잡몹과 보스 1종을 구현했습니다.

GitHub — 공개 준비 중

01 시작 전에 본 리스크

시작 전에 아래 세 가지를 이 프로젝트의 리스크로 봤습니다.

누가 어떤 AI로 코드를 쓰든, 커밋과 PR을 통과하지 못하면 들어올 수 없게 만드는 것이 이 프로젝트의 기본 전략이었습니다.

01처음 쓰는 네트워크

팀 전원이 Fusion 2가 처음이었습니다. 네트워크 코드는 틀렸을 때 조용히 틀립니다.

02빨라진 손

AI는 작업 속도를 크게 올려 주지만, 속도가 오른 만큼 잘못된 방향으로도 빨리 갑니다.

03제각각인 도구

시작 시점에는 팀원마다 쓰는 AI가 달랐습니다. Claude Code, Codex CLI, 웹 LLM이 섞여 있었고, 특정 도구에만 규칙을 설정하는 방식으로는 팀 전원에게 적용할 수 없었습니다.

02 팀이 구현한 것

약 2개월 반 동안 4인이 작업했습니다. 아래 중 네트워크 · 초기 무기 시스템 · 잡몹 · 보스 1종 · 사운드 재생 프레임워크 · DB · Stove SDK 연동 · 빌드/배포, 그리고 가드레일 전반이 제 담당입니다.

Networking

Fusion 2 Hosted Mode 세션(최대 4인), 권한 헬퍼, 로비 · 방 관리, 입장 투표.

Combat

무기, 기본공격, 궁극기와 체인 / 풀체인(팀 협동 공격), 데미지 · 쿨다운, CC와 지속 디버프.

BossContent · Dungeon

보스 AI · 패턴 · 페이즈 · 기믹, 스테이지 미션 진행과 구역 개폐, 웨이브 오케스트레이션.

World · Minions

파괴 가능 타일, 확률 드랍과 루트 테이블, 잡몹 스폰과 추적.

UI · Sound · DataBases

HUD와 체인 게이지, BGM · SFX, 플레이어 · 캐릭터 데이터 저장.

BuildDeploy · SDK

빌드 스크립트와 CI, 그리고 출시를 전제로 한 STOVE PC SDK 연동.

03 팀장으로서 맡은 일

경계를 합의가 아니라 도구로 세우는 것이 이번 역할의 핵심이었습니다.

모듈 경계 설계

모듈을 어셈블리 정의(*.asmdef)로 분리하고 의존 방향을 단방향 DAG로 고정했습니다. 위로 참조하면 컴파일되지 않습니다.

정적 검사 스크립트

결정론 · 서버 권한 · 단일 출처처럼 asmdef가 못 잡는 규칙을 파이썬 검사 스크립트로 옮겼습니다.

pre-commit 훅 · PR CI

같은 스크립트를 로컬 커밋(1차) 과 PR 워크플로(최종 게이트) 양쪽에서 돌립니다. 로컬은 우회할 수 있지만 CI는 못 합니다.

에이전트 하네스

주요 모듈에 CLAUDE.md와 담당 서브에이전트를 두어, AI가 자기 모듈 폴더만 수정하도록 제한했습니다.

문서 동기화 자동화

공개 API 문서와 Codex용 미러 문서를 생성물로 두고, 소스와 어긋나면 커밋을 막습니다.

구현 — 네트워크 · 무기 · 적

Hosted 세션과 권한 헬퍼, 초기 무기 시스템, 잡몹 두 갈래와 GreatMushroom 보스전을 맡았습니다.

04.1 고민과 해결 — 규칙을 사람이 아니라 도구가 지키게

규칙을 문서로만 두면, 지켜지는지 확인하는 일이 매번 사람의 몫이 됩니다.

문제

이전 프로젝트에서 AI를 남용한 결과 나쁜 구조가 그대로 굳어지는 것을 겪었습니다. AI는 가장 그럴듯하게 동작하는 코드를 쓸 뿐, 우리 팀의 경계를 알지 못합니다.

이번에도 같은 문제가 예상됐습니다. 게다가 시작 시점에는 팀원마다 쓰는 AI가 달라, 특정 도구에만 규칙을 설정하는 방식으로는 팀 전원에게 적용할 수 없었습니다.

관점

규칙은 프로젝트 안에 문서로 두어 사람과 AI가 같은 것을 읽게 하고, 이를 지키지 않으면 진행이 안 되도록 강제해야 한다고 봤습니다.

그래서 그 검사를 도구가 아니라 리포지토리에 걸기로 했습니다. 누가 어떤 AI를 쓰든 커밋과 PR을 통과해야 코드가 들어옵니다.

해결
  • 컴파일 · 모듈을 어셈블리 정의(*.asmdef)로 나누고 의존 방향을 단방향으로 고정했습니다. 공유 타입은 Game.Core에만 두고, 형제 모듈은 서로를 참조하지 않고 Core 이벤트로만 대화합니다. 어긴 코드는 빌드되지 않습니다.
  • 커밋 · PR · 서버 권한 없는 상태 변경, 결정론을 깨는 시간·난수, 단일 출처 위반처럼 컴파일러가 못 잡는 규칙은 텍스트로 드러나므로 정적 검사 스크립트로 옮겼습니다. pre-commit 훅이 1차로, PR CI가 최종 게이트로 같은 스크립트를 돌립니다. 로컬 훅은 우회할 수 있지만 CI는 우회할 수 없습니다.
  • 문서 · 도구마다 읽는 파일이 다르므로 규칙 문서의 단일 출처를 한 곳으로 두고 나머지는 전부 생성물로 만들었습니다. 소스와 어긋나면 커밋이 막힙니다.

정당한 예외는 지우는 것이 아니라 위반 줄에 억제 주석으로 남겨, 리뷰에서 사유를 확인하는 대상이 되게 했습니다.

04.2 고민과 해결 — 잡몹을 두 갈래로 나눈 것

기획에는 성격이 다른 두 종류의 잡몹이 있었습니다. 몇 마리에서 십여 마리가 플레이어와 붙어 싸우는 잡몹과, 수천 마리가 몰려나오는 잡몹입니다.

문제

둘 다 “잡몹”이라는 한 단어로 불리지만, 네트워크 비용 구조가 전혀 다릅니다. 개체마다 NetworkObject를 붙이는 방식은 소수일 때는 가장 단순하고 확실하지만, 마릿수에 비례해 동기화 비용이 늘어납니다.

반대로 대량을 감당하는 구조를 하나 만들어 두고 소수 잡몹까지 거기에 태우면, 몇 마리 안 되는 적 하나를 만드는 데도 과한 복잡도를 치러야 합니다. 어느 한쪽에 맞추면 다른 쪽이 손해를 보는 구조였습니다.

관점

처음부터 별개의 시스템으로 갔습니다. 이름이 같다는 이유로 한쪽에 맞춰 통합하면 양쪽 모두가 불편해진다고 봤습니다.

대신 두 모듈을 완전히 독립으로 두고, 서로 참조하지 못하게 했습니다. 바깥에서 보면 둘 다 IDamageable을 구현한 적일 뿐이라, 때리는 쪽 코드는 어느 경로인지 알 필요가 없습니다. 무기는 맞은 콜라이더에서 IDamageable을 찾아 데미지를 넘길 뿐입니다.

해결
  • 소수 잡몹 — GameObject 경로 · 개체마다 NetworkBehaviour를 두고 [Networked] 상태로 FSM(Idle · Walk · Attack · Dying)을 돌립니다. 스폰은 풀을 거쳐 재사용하고, 디스폰은 파괴가 아니라 비활성화입니다. 한 마리씩 다르게 행동해야 하는 적에 맞는 방식입니다.
  • 대량 잡몹 — ECS 경로 · 수천 마리가 동시에 존재하므로 개체를 아예 동기화하지 않습니다. 각 피어가 자기 ECS 월드를 따로 굴리고, 애니메이션도 본 대신 VAT(정점 애니메이션 텍스처)로 재생합니다. 제가 맡은 GreatMushroom 보스전이 이 경로를 씁니다.
  • 피어마다 다른 잡몹을 본다 · 개체를 맞추지 않으므로 내 화면의 잡몹 배치와 남의 화면이 다릅니다. 대신 플레이어가 겪는 결과 — 누가 얼마나 맞았고 몇 마리를 잡았는지 — 만 맞춥니다.

배치가 피어마다 다르면 “저 잡몹”을 가리킬 방법이 없습니다. 그래서 개체를 가리키는 통신을 아예 두지 않고, 판정은 각 피어가 자기 월드에서 끝냅니다. 

// 개체는 오가지 않는다 — 복제되는 것은 숫자뿐
플레이어 → 잡몹   전송 없음. 공격 범위에 걸린 셀의 잡몹을 자기 월드에서 죽인다
                  피격 판정의 단위가 개체가 아니라 격자 셀이다

잡몹 → 플레이어   각 피어가 자기 로컬 플레이어에 대해서만 피격을 판정
                  (남의 피해까지 판정하면 그 사람 화면엔 붙지도 않은 잡몹에게 맞는다)
                  HP 적용은 호스트가 하고, 클라는 “맞았다”고 신고만 한다

복제되는 상태     플레이어별 잡몹 수가 사실상 전부다
                  각자 자기 수를 보고하고 호스트가 모아 되뿌린다

05 AI 활용 범위

혼자 AI를 잘 쓰는 것과 팀 전체가 AI를 쓰는 것은 다른 문제였습니다. 후자는 각자의 AI가 같은 규칙을 읽게 만드는 일에 가까웠습니다.

맡긴 것

처음 다루는 Fusion 2 API 조사, 모듈 내부 구현의 초안 작성, 디버깅 보조, 그리고 가드레일 검사 스크립트 구현입니다. 검사 스크립트는 무엇을 검사할지와 모듈 방향만 제가 정하고, 코드는 전부 AI가 썼습니다.

맡기지 않은 것

경계와 규칙, 그리고 git은 사람이 잡았습니다. AI가 잘하는 것은 “주어진 자리에서 그럴듯한 코드를 빨리 쓰는 일”이고, 자리를 정하는 일은 사람 몫이라고 봤습니다.

규칙을 AI가 읽는 자리에

모듈 폴더에 CLAUDE.md를 두어, 그 모듈에서 작업하는 AI가 경계와 네트워크 규칙을 먼저 읽도록 했습니다. 잘못된 코드를 잡아내는 대신 처음부터 덜 나오게 하는 층입니다.

행동 원칙까지 문서로

안드레이 카파시(Andrej Karpathy)의 지침을 반영해 “가정하지 않는다 · 요청받지 않은 기능을 넣지 않는다 · 필요한 줄만 고친다”를 루트 규칙에 넣었습니다. AI의 과잉 생산이 리뷰 비용으로 돌아오는 것을 줄이려는 목적이었습니다.

도구 중립

가드레일을 파이썬 스크립트와 git 훅으로 만들었기 때문에, 도구가 서로 다를 때도 나중에 전원이 Claude로 옮겼을 때도 규칙은 그대로 작동했습니다.

06 결과 평가

약 2개월 반, 1,800여 개의 커밋이 쌓였습니다. 지금 시점에서의 판단을 적습니다.

잘 된 점
프로젝트 초기에 가드레일을 설정한 덕분에, 전원이 처음 쓰는 네트워크 프레임워크 위에서, 서로 다른 AI로 출발해, 4인이 두 달 반 동안 49,000줄을 쌓고도 후반을 개발과 출시 준비(STOVE SDK 연동)에 나눠 쓸 수 있었습니다.
배운 점
검사받지 않는 문서는 낡는다는 것을 한 프로젝트 안에서 대조적으로 확인했습니다. API 문서와 미러 문서는 훅이 검사한 덕에 끝까지 소스와 맞았지만, 신선도 검사를 걸어 두지 않은 모듈별 에이전트 지침은 나중에 추가된 모듈에서 빠진 채로 남았습니다.

네트워크 게임은 레이어를 먼저 나누고 시작해야 한다는 것도 배웠습니다. 이번에는 어떤 상태가 어느 경로로 오가는지가 코드 곳곳에 흩어져 있어 동기화 문제의 원인 파악이 더뎠습니다.
아쉬운 점
일부 콘텐츠는 권한이 여전히 클라이언트에 남아 있습니다. 강화는 요청을 호스트에 보내고 결과를 클라이언트가 받는 형태지만, 요청 자체가 정당한지를 호스트가 검증하지 않습니다.

ECS 잡몹은 시뮬레이션 상태를 동기화하는 것 자체가 부담이라고 보고 각 피어가 자기 월드를 따로 돌리게 두었습니다. 수천 마리의 위치와 상태를 맞추는 비용을 감당할 자신이 없어 처음부터 동기화를 포기한 선택이었고, 그 대가로 피어마다 다른 화면을 감수해야 했습니다. 나중에 Netcode for Entities가 같은 규모를 어떻게 맞추는지 찾아보니 결국 상태를 패킹해서 주고받는 방식이었습니다. 포기할 문제가 아니라 아키타입을 그에 맞게 설계할 문제였고, 다음에 같은 것을 만든다면 그 지점부터 잡으려 합니다.
총평
전원이 처음 쓰는 프레임워크에 서로 다른 AI까지 겹친 조건에서, 규칙을 리포지토리에 강제로 걸어 두는 방식이 실제로 작동한다는 것을 확인했습니다. 다음에는 같은 방식을 에이전트 지침의 신선도와 네트워크 레이어 분리까지 적용하려 합니다.

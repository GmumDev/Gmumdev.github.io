KDT 훈련과정에서 주어진 첫 프로젝트형 과제입니다. 엔진도 그래픽 API도 없이 Console만 있는 환경이었기 때문에, 평소 엔진이 대신 해주던 일 — 렌더 루프, 화면 레이아웃, 오브젝트 업데이트 순서 — 을 전부 직접 정해야 했습니다. 그 결정들을 남깁니다.

01 과제 요구사항과, 제가 덧붙인 것

요구사항 자체는 짧았습니다. 몬스터를 모두 잡으면 맵 클리어, 문을 통과하면 다음 맵에서 반복, 그리고 Json 세이브/로드. 여기에 세 가지를 더했습니다.

01절차적 생성

고정 맵 대신 매 스테이지를 생성하기로 했습니다. 생성기가 만든 맵이 항상 클리어 가능한지를 보장하는 문제가 이 프로젝트에서 가장 재미있었습니다.

02직접 만든 UI

콘솔에는 UI 시스템이 없으므로 박스 단위의 렌더 계층을 만들었습니다. 미니맵 · 인벤토리 · 상점 · 팝업이 모두 같은 규칙 위에 올라갑니다.

03특수 몬스터

한 칸짜리 몬스터만으로는 맵이 단조로워서, 여러 칸을 차지하고 스스로 움직이는 Snake 계열을 넣었습니다.

02 구현한 피처

Program이 DungeonGame 인스턴스를 만들어 Play()를 호출하면, 스테이지를 생성해 그리드 위에 맵들을 배치하고 시작 맵을 현재 맵으로 잡은 뒤 메인 루프에 들어갑니다. 루프는 입력 한 번이 한 턴입니다. 

// 메인 루프 (입력 한 번 = 한 턴)
1. 현재 맵의 모든 엔티티를 Update
2. 플레이어 입력을 받는다
   ├ W A S D  이동할 칸의 Entity.OnPlayerEnter() 호출
   │          — 피해 · 이동 불가 · 제거 후 이동을 엔티티가 스스로 처리
   │          — 엔티티 혼자 처리할 수 없는 세 경우만 게임 루프가 받는다
   │          ├ Door 이고 맵을 클리어했다면        → 다음 맵으로
   │          ├ NextStageBicon 이고 스테이지 클리어 → 다음 스테이지로
   │          └ 처리 결과 플레이어가 죽었다면       → GameOver 팝업
   └ Q        SaveLoad 팝업 (저장 · 불러오기 · 재개 · 재시작 · 종료)
3. Renderer가 화면에 정보를 그린다

아래는 이 루프 위에 올라간 요소들입니다.

스테이지 · 맵

7×7 그리드 위에 방 3~7개를 배치합니다. 각 방은 크기가 제각각이며, 그리드 상 인접한 방끼리 벽 중앙의 Door로 연결됩니다. 모든 방을 클리어하면 끝 방의 NextStageBicon으로 다음 스테이지에 진입합니다.

엔티티

맵은 Entity[,] 2차원 배열 그 자체입니다. 빈 칸도 EmptyEntity라는 실체를 가지므로 null 검사가 필요 없고, 이동은 언제나 두 칸의 Swap으로 표현됩니다.

미니맵

스테이지 그리드를 그대로 지도로 씁니다. 현재 방을 항상 화면 중앙에 두고 다른 방들을 상대 좌표로 그립니다.

상점 · 인벤토리

시작 방에 ItemShop이 놓이고, ItemDBContainer에서 아이템 정보를 받아 포션 3종을 판매합니다. 구매한 아이템은 InventoryBox에 표시됩니다.

팝업 UI

게임 오버 · 일시정지(세이브/로드) · 상점이 모두 AlertRenderBox 하나로 구현됩니다. 키 하나에 콜백 하나를 등록하는 방식입니다.

세이브 · 로드

System.Text.Json으로 진행 중인 스테이지 · 맵 · 플레이어 상태를 통째로 저장하고 복원합니다.

03 주요 클래스 구조

게임 로직 계층(Stage · Map · Entity)과 표현 계층(Renderer · RenderBox)을 나누고, 둘을 IRenderable 하나로 연결했습니다.

Entity

IEntity + IRenderable을 구현한 추상 클래스입니다. 핵심은 OnPlayerEnter()가 string을 반환한다는 점입니다. 각 엔티티는 플레이어가 자기 칸에 들어왔을 때의 처리(피해 · 이동 불가 · 소멸 · 구매)를 스스로 하고, 화면에 띄울 메시지만 돌려줍니다. 게임 루프는 그 문자열을 MsgRenderBox에 넘길 뿐이라 엔티티를 하나도 알지 못합니다.

Map

IMapDataModifier를 구현해 SetEntity · GetEntity · Swap만 외부에 노출합니다. 클리어 조건은 필드가 아니라 ClearChecker 대리자라서, 방을 채우는 방식마다 다른 조건을 꽂아 넣을 수 있습니다.

StageFactory · MapFactory

방의 배치(어디에 몇 개, 어떻게 연결)는 StageFactory가, 방의 내용물(무엇으로 채울지)은 MapFactory가 담당합니다. 이 분리 덕분에 “맵 종류 추가”는 MapFactory에 채우기 함수 하나를 더하는 일이 됩니다.

Renderer · RenderBox

RenderBox는 자기 크기의 char[,] 버퍼와 여백(margin)을 가진 추상 블록입니다. Renderer는 전체 화면 버퍼를 갖고 있고, 각 박스가 자기 버퍼에 그린 결과를 그 위로 합성합니다.

04.1 고민과 해결 — 던전 생성

완전 무작위로 방을 뿌리면 시작 방에서 끝 방까지 이어지지 않는 스테이지가 나옵니다.

문제

방을 랜덤 좌표에 배치하면 연결성과 방 개수를 동시에 만족시키기 어렵습니다. 연결을 먼저 보장하려 하면 결국 한 줄로 늘어선 복도가 되고, 개수를 먼저 채우면 섬처럼 떨어진 방이 생깁니다.

미니맵도 “스테이지 전체를 어떻게 좌표로 표현할 것인가”라는 같은 문제를 안고 있었습니다.

관점 전환

방을 자유 평면이 아니라 7×7 그리드 위의 칸으로 두기로 했습니다. 그러면 “인접한가”가 좌표 뺄셈 한 번으로 판정되고, 스테이지 자체가 곧 그래프가 됩니다.

미니맵은 이 그리드를 그대로 그리면 되므로, 자료구조 하나가 생성 · 연결 · 표시 세 가지를 동시에 해결했습니다.

해결 — 메인 경로 먼저, 곁방은 나중에
  • 1. 개수와 양 끝 결정 — 방 개수를 3~7 중에서 뽑고, 시작 칸을 랜덤으로 정합니다. 끝 칸은 맨해튼 거리가 방 개수보다 작은 칸 중에서 고릅니다. 이 조건 하나로 “방이 모자라 끝에 닿지 못하는” 경우가 원천적으로 사라집니다.
  • 2. 메인 경로 — 시작에서 끝까지 최단 경로를 따라가되, x축과 y축 중 어느 쪽을 먼저 줄일지를 매 칸 랜덤으로 정합니다. 결과는 항상 최단 경로이면서 매번 모양이 다릅니다.
  • 3. 곁방 — 남은 개수만큼, 이미 배치된 방 중 하나를 골라 인접한 빈 칸에 방을 추가합니다. 새로 생긴 곁방도 후보 집합에 합류하므로 곁방에서 다시 곁방이 뻗어 나갑니다. 어떤 방도 기존 방과 붙어서 생기기 때문에 연결성은 계속 유지됩니다.
  • 4. 문 연결 — 배치가 끝나면 각 방이 네 방향 이웃을 훑어 Door를 만들고 서로를 참조시킵니다.
  • 5. 클리어 조건 — 스테이지의 IsClear는 “그리드 위 모든 방의 IsClear가 참”인 람다로 조립됩니다.

방의 내용물은 MapFactory가 List<FillUpMapDelegate>에서 하나를 랜덤으로 골라 채웁니다 (기본 · Snake · Snake 알 · BigSnake). 시작 방과 끝 방만 전용 함수로 고정됩니다. 새 방 유형을 늘리려면 함수를 하나 쓰고 리스트에 넣기만 하면 됩니다. 

// 방의 종류 = 채우는 방법. 목록에 추가하는 것만으로 늘어난다.
FillUpMapTasks.Add(FillUpMap_Default);
FillUpMapTasks.Add(FillUpMap_Snake);
FillUpMapTasks.Add(FillUpMap_SnakeGrowUp);
FillUpMapTasks.Add(FillUpMap_BigSnake);

// 채우는 방법이 그 방의 클리어 조건까지 함께 정한다.
map.IsClear = () => map.GetMapData()["monster_cnt"] == 0;

04.2 고민과 해결 — 막힌 맵이 나오지 않게

방 안에도 장애물(Fence)을 뿌려야 하는데, 이게 길을 끊어버릴 수 있었습니다.

문제

방 넓이의 약 17%를 장애물로 채우다 보니, 몬스터가 벽에 둘러싸여 잡을 수 없거나 문에서 문으로 지나갈 수 없는 방이 종종 생성됐습니다. 클리어 조건이 “모든 몬스터 처치”이므로 이건 곧 진행 불가입니다.

네 개의 문 중 어느 문으로 들어올지는 플레이어가 정하므로, 어느 문에서 출발하든 모든 몬스터와 모든 문에 닿을 수 있어야 했습니다.

판단

장애물을 “길을 막지 않도록 조심해서 놓는” 규칙을 만드는 대신, 일단 놓고 검사한 뒤 실패하면 다시 놓기로 했습니다.

방 크기가 작고(최대 60×45) 실패 확률이 낮아 재시도 비용이 무시할 만했고, 무엇보다 배치 규칙과 검증 규칙이 분리되어 이후에 어떤 배치 방식을 추가해도 검증이 그대로 재사용됩니다.

해결 — 네 문에서 각각 BFS, 그리고 교집합

“모든 출발점에서 닿는 칸”은 각 출발점의 도달 집합을 교집합한 것과 같습니다. 네 개의 문 각각에서 BFS를 돌려 도달 가능한 칸 집합을 구하고, 그 교집합이 반드시 닿아야 하는 칸(몬스터 · 문)을 모두 포함하는지만 확인하면 됩니다. 

// 배치 → 검증 → 실패 시 재배치
do {
    GetRandomEmptyPos(map, ref fencePos, many);           // 후보 배치
    GetReachables(map, ref reachables, doors, ..., fencePos);
    flag = endPos.All(p => reachables.Contains(p));       // 몬스터·문이 모두 도달 가능한가
} while (flag == false);

// GetReachables 내부: 각 문에서 BFS한 결과를 교집합
visited.UnionWith(subVisited[0]);
for (int i = 1; i < starts.Length; i++)
    visited.IntersectWith(subVisited[i]);
  • 후보 상태로 검사 — Fence 객체를 실제로 만들기 전, 좌표 집합만으로 BFS의 통행 금지 칸을 흉내 냅니다. 검증에 통과한 좌표에 대해서만 엔티티를 생성하므로 실패한 시도가 맵을 오염시키지 않습니다.
  • 목표 지점의 정의 — 반드시 닿아야 하는 칸은 “처치해야 하는 몬스터”와 “문”입니다. Snake 계열은 처치가 클리어 조건이 아니므로 이 목록에서 빠집니다 — 클리어 조건과 검증 대상이 같은 곳을 바라보도록 맞춘 부분입니다.

04.3 고민과 해결 — 콘솔에 화면을 그리기

엔진이 대신 해주던 일 중 가장 티가 나는 것이 렌더링이었습니다.

문제

Console.WriteLine을 여러 번 호출하면 화면이 눈에 띄게 깜빡입니다. 맵 · 미니맵 · 메시지 · 플레이어 정보 · 인벤토리 · 입력창을 각각 출력하면 그 횟수만큼 깜빡임이 늘어납니다.

여기에 각 정보를 화면 어디에 배치할지도 직접 계산해야 했습니다.

해결

출력과 그리기를 나눴습니다. 모든 요소는 char[,] 버퍼에 그리기만 하고, 최종적으로 Renderer가 전체 버퍼를 StringBuilder로 이어 붙여 한 번만 출력합니다. 커서를 (0, 0)으로 되돌리고 덮어쓰므로 화면 클리어도 필요 없습니다.

Entity와 RenderBox가 같은 IRenderable.Render(char[,] parentBuf)를 구현합니다. 엔티티는 맵의 버퍼에, 박스는 화면 버퍼에 그리는 같은 형태의 재귀적 합성입니다.

레이아웃

각 박스의 여백을 이전 박스의 여백 + 크기로 계산해 연쇄시켰습니다. 맵 박스 오른쪽에 미니맵, 그 오른쪽에 메시지, 미니맵 아래에 플레이어 정보 — 하드코딩된 좌표 없이 순서만으로 배치가 정해집니다.

미니맵

현재 방을 항상 화면 중앙(┼)에 고정하고, 다른 방들을 그리드 좌표 차이에 배율 3을 곱한 위치에 3×3 테두리 문자로 그립니다. 플레이어가 이동하면 지도가 따라 흐릅니다.

팝업

AlertRenderer가 발생한 팝업 큐 → 입력 → 콜백 큐 순서로 처리합니다. SetCallback('S', "Save", SaveGame)처럼 키 · 표시 문구 · 동작을 한 줄로 등록하므로, 게임 오버 · 일시정지 · 상점이 모두 같은 클래스입니다.

04.4 고민과 해결 — 여러 칸을 차지하는 몬스터

한 칸에 하나씩 놓인 몬스터를 순서대로 잡는 것만으로는 방이 단조로웠습니다. “머리와 꼬리가 이어져 스스로 기어 다니는” 몬스터를 넣기로 했습니다.

몸통 이동

Snake_Head가 List<Entity> bodies로 자기 몸을 들고 있습니다. 매 턴 인접한 빈 칸 중 하나로 머리를 옮기고, 각 마디를 바로 앞 마디의 직전 위치로 밀어 넣습니다. 좌표를 새로 계산하지 않고 Map.Swap만 반복하므로 맵의 무결성이 저절로 지켜집니다.

갇힘 처리

사방이 막혀 5턴 동안 움직이지 못하면 몸 전체를 뒤집습니다(머리와 꼬리를 맞바꿈). 구석에 박혀 영원히 멈춰 있는 상태를 코드 몇 줄로 벗어납니다.

다른 클리어 조건

Snake는 잡을 수 없습니다(닿으면 피해). 대신 일정 턴이 지나면 매 턴 확률적으로 꼬리 끝에 MapClearBicon을 뱉고, 플레이어가 그것을 주우면 방이 클리어됩니다. 확률은 턴마다 조금씩 올라가 기다림이 무한정 길어지지 않도록 했습니다.

변주 — 상속과 성장

BigSnake_Head는 Snake_Head를 상속해 AddTail()을 더 부르는 것이 전부입니다. SnakeBaby는 20~40턴 뒤 Snake_Head로 자라며, 부화 5턴 전부터 기호가 바뀌어 플레이어에게 경고합니다.

덤으로 만난 문제 — 한 턴에 두 번 움직이는 몬스터

맵을 2차원 배열 순서대로 순회하며 Update()를 호출하는데, 엔티티가 아직 순회하지 않은 칸으로 이동하면 같은 턴에 한 번 더 갱신됩니다. IsUpdatedOnCurFrame 플래그를 턴 시작에 일괄 초기화하고 갱신 직전에 세우는 것으로 막았습니다. “순회 중에 순회 대상이 움직인다”는 문제를 처음 제대로 만난 지점이었습니다.

05 세이브 · 로드

런타임 객체를 그대로 직렬화할 수 없다는 것을 처음 체감한 부분입니다.

Raw 구조체

런타임 객체는 서로를 참조합니다 — Door는 옆 방을, 엔티티는 맵을. 이 그물을 그대로 Json으로 만들 수 없어서, 순환 참조가 없는 평평한 구조체(RawGameData · RawStageData · RawMapData · RawPlayerData · RawItemData)를 따로 정의했습니다.

RawDataParser

런타임 객체 ↔ Raw 구조체 변환만 담당하는 static 어댑터입니다. 게임 클래스도 Utility의 Json 함수도 서로를 모르는 채로, 저장 형식이 바뀌어도 이 클래스만 고치면 됩니다.

복원 경로 분리

새 게임은 SetNewStage(), 불러오기는 SetNewStageWithRawData()로 나뉩니다. 후자는 랜덤 채우기를 건너뛰고 저장된 엔티티 배치를 그대로 복원한 뒤, 문 연결만 다시 계산합니다.

실패 처리

저장 파일이 없으면 예외를 잡아 “No Saved Data” 메시지로 대체합니다. 게임을 중단시키지 않고 메시지 박스로 흘려보내는 방식입니다.

06 결과 평가

1주짜리 첫 과제였고, 지금 다시 보면 눈에 밟히는 것이 많습니다.

달성
요구사항(맵 클리어 · 맵 이동 · Json 세이브/로드)을 모두 충족했고, 그 위에 절차적 던전 생성 · 도달 가능성 보장 · 미니맵 · 박스 UI · 상점 · Snake 계열 몬스터를 더했습니다. 무엇보다 완주 가능한 게임 사이클이 돌아갑니다.
배운 점
엔진 없이 만들면서 업데이트 순서 · 렌더 버퍼 · 레이아웃 계산이 원래 누가 해주던 일인지를 알게 됐습니다. “배치하고 검증하고 실패하면 다시”라는 접근은, 규칙을 완벽하게 설계하는 것보다 검증을 분리하는 편이 나을 때가 있다는 것을 알려줬습니다.
아쉬운 점
Entity.map이 static입니다. 모든 엔티티가 현재 맵 전체를 수정할 수 있다는 뜻이라, 작성 당시에도 // too many authority라는 주석을 달아 두었으면서 끝까지 고치지 않았습니다. 맵의 상태를 Dictionary<string, int>로 들고 "monster_" + i + "_x"처럼 문자열을 조합해 접근하는 부분도 타입 안전하지 않고 오타에 무방비합니다 — 전용 구조체였어야 했습니다. StageFactory는 이름과 달리 생성뿐 아니라 스테이지 보관 · 조회까지 겸하고 있어 책임이 둘입니다.
구조적 한계
장애물 배치의 재시도 루프(do-while)는 종료가 보장되지 않습니다. 지금의 방 크기와 장애물 비율에서는 실질적으로 문제가 없지만, 비율을 올리면 무한 루프에 빠질 수 있으므로 시도 횟수 상한과 실패 시 완화 전략이 있어야 했습니다. Snake_Head는 이동 · 성장 · 비콘 생성 · 갇힘 탈출을 Update() 하나에서 처리해 길고, 상태로 분리하는 편이 나았습니다.
총평
요구사항을 채우는 데서 멈추지 않고 스스로 문제를 하나 더 만들어 푼 것이 이 과제에서 가장 잘한 선택이었다고 생각합니다.

Simple RPG

싱글 플레이 RPG · 개인 · 1개월 · Unity 6.3 · C#

많은 요소가 유기적으로 연결되면서도 유지보수가 가능한 구조를 만들어 보고 싶어 RPG를 택했습니다. 시스템이 하나씩 늘어날 때마다 구조의 한계가 드러났고, 그 지점들과 해결 과정을 남겼습니다.

01 설계 의도

개발 컨셉은 “RPG의 다양한 기능 구현”이었고, 기획 의도는 세 가지였습니다.

01장르 확장성

RPG의 메인 피처들은 RPG 외 다양한 장르에서도 응용이 가능하다고 판단했습니다.

02결합의 문제 경험

대규모 프로젝트의 기능을 구현하고 결합하는 과정에서 발생하는 문제를 직접 겪어보기 위해서였습니다.

03구조 설계 능력

프로젝트 구조 설계 능력을 끌어올리는 것이 목표였습니다.

02 구현한 피처

게임 흐름은 Title → Init(비동기 인게임 · 세이브 데이터 로딩) → World ⇄ Dungeon으로 순환합니다.

시나리오

단방향 LinkedList 구조의 노드 기반 시나리오. 선택지 분기와 이벤트 발생을 지원하며, 퀘스트 시작 · 완료, 지역 해금, 시나리오 해금 등을 트리거합니다.

퀘스트

이름 · 내용 · 다중 조건 · 다중 보상으로 구성되며, 수락 → 진행 → 완료 사이클을 따릅니다.

전투

캐릭터 교체와 파티 구성, 캐릭터별 스킬 분리, 태그 스킬, 쿨타임 출력. 보스는 가중치 기반 패턴 선택으로 동작합니다.

인벤토리

드래그로 아이템 위치 교체와 버리기, 최대 64개까지 스택.

성장 · 아이템 드롭

레벨별 스탯 테이블로 최대 체력 · 최대 경험치 · 공격력 · 방어력을 적용합니다. 몬스터 처치 시 아이템은 즉시 획득되고, 경험치는 플레이어가 근접하면 약한 인력이 작용합니다.

상호작용 · 이동

NPC 시나리오 재생, 맵을 둘러보는 타임라인과 시야 오브, 채집. 포탈(트리거)과 게이트(NPC)로 World ⇄ Dungeon 간 비동기 씬 로드를 처리합니다.

03 주요 클래스 구조

RPG 장르로서의 확장성을 적극적으로 고려하고, SOLID를 준수하도록 노력했습니다.

Player

Player가 Orchestrator 역할을 수행하는 계층적 FSM 구조입니다. 데이터와 로직을 분리해 SRP를 지키고자 했습니다.

Scenario

하나의 시나리오 정보를 담는 ScriptableObject가 시나리오 노드 LinkedList의 Head를 참조합니다. 직렬화 데이터(SO)와 런타임 데이터(Context)를 분리하고, IScenarioManager · IScenarioCtxRunner로 인터페이스를 쪼개 ISP를 적용했습니다.

Quest

IQuestManager(API)와 IQuestRewardEarner(보상 지급)로 역할을 분리했습니다. 각 Service가 추상 Handler를 참조하고 구체 Handler가 실제 로직을 수행하므로, 예를 들어 특정 지역 방문 조건이 필요하면 IConditionChecker를 상속한 VisitChecker만 구현하면 됩니다 — OCP.

UI

Normal · Watching · Battle State마다 성격이 다른 UI가 필요했습니다. Player가 각 State에 진입할 때 UIFSM.ChangeState()를 호출하고, UI State가 실제 게임오브젝트를 토글합니다. 구체 로직은 각 Sub-UI 클래스가 EventBus로 관련 이벤트를 구독해 처리합니다.

04.1 고민과 해결 — EventBus

시스템이 늘어날수록 객체 간 의존이 어떻게 번지는지를 가장 직접적으로 체감한 부분입니다.

문제

Enemy.Die() 하나가 호출될 때 UI 갱신, 아이템 드롭, 퀘스트 진행도 갱신, 파티클 풀링이 뒤따랐습니다. Enemy가 다른 클래스에 대해 갖는 의존이 급격히 증가했고, 기능이 추가될 때마다 코드가 한 줄씩 늘었습니다.

여기에 사운드를 하나 추가한다면 Enemy뿐 아니라 거의 모든 오브젝트 클래스에 한 줄씩을 더해야 했습니다.

1차 시도

event Action 대리자로 Enemy.OnKilledEvent += Listener 방식의 구독을 도입했습니다.

그러나 대리자를 매번 직접 선언해야 했고, 여러 이벤트를 구독하면 각각을 따로 해지해야 했습니다. 무엇보다 Enemy를 수정하지 않아도 대리자에 접근하기 위해 결국 의존성이 발생했습니다.

해결

static 클래스 EventBus를 구현하고, 복잡한 이벤트는 이 객체를 통해 구독 · 해지하도록 했습니다.

  • 디커플링 — 이벤트를 대리자가 아닌 클래스로 구현했습니다. 내부적으로 Action<T>의 T가 이 클래스이므로, 이벤트 매개변수를 한 번 감싼 래퍼 역할을 합니다. 구독자는 이벤트를 호출한 객체를 전혀 알 필요가 없습니다.
  • 안정성 — 구독 시 SubscriptionToken 인스턴스를 반환하고 해지 시 인자로 전달받습니다. 따라서 리스너를 람다로 작성하더라도 토큰만 있으면 안전하게 해지할 수 있습니다.
  • 확장성 — 새 이벤트가 생겨도 발행자 코드를 건드리지 않습니다.

04.2 고민과 해결 — Animator와 FSM 동기화

가장 오래 붙들었던 문제이자, 기술 선택에 대한 판단을 다시 하게 만든 지점입니다.

문제

StateMachineBehaviour 기반 플레이어 상태머신은 Animation과 분리되어 동작할 수 없었습니다.

결정적으로 Animator의 Transition은 현재 상태의 OnExit 이후에 새 상태의 OnEnter가 호출되는 것을 보장하지 않습니다. Transition 기간이 길면 두 애니메이션이 겹치는 Blend 구간 때문에 진입이 먼저, 퇴장이 나중에 호출됩니다. 무결성 문제이자 기능 확장의 걸림돌이었으므로 커스텀 FSM으로 옮기기로 결정했습니다.

그런데

옮기고 나니 이번엔 애니메이션 싱크가 어긋났습니다. 기존에는 Player@Battle에서 Player@OnHit으로 애니메이션이 전환되면 Battle의 StateMachineBehaviour가 업데이트되지 않아 경직이 자연스럽게 구현되었습니다.

커스텀 FSM에서 같은 경직을 만들려면 State를 OnHitState로 바꾸고, 애니메이션 종료를 감지한 뒤 다시 BattleState로 되돌려야 했습니다. 그런데 이 상태가 하는 일은 종료 감지뿐이었습니다.

해결

역할이 감지뿐이라면 이름도 그래야 한다고 보고 WaitForAnimState로 정리한 뒤, 모든 전환을 두 갈래로 나눴습니다. 

// 1. State가 Animation 재생을 결정한다면 → 즉시 전환
ChangeState(nextState);

// 2. Animation 재생 여부가 State를 결정한다면 → 대기 전환
void WaitForAnim(string fromTag, string toTag, State nextState);
  • 즉시 전환 — Animator 트리거를 활성화함과 동시에 State를 전환합니다.
  • 대기 전환 — 피격 · 공격 애니메이션이 끝날 때까지, 또는 사망 후 부활 버튼을 누를 때까지 기다렸다가 전환합니다.
  • 유연성 — Animator의 각 Node에 Tag를 입력해 두고 Tag 간 이동을 감지합니다. fromTag나 toTag에 "Any"를 전달하면 해당하는 모든 Tag를 허용하고, 대기 도중 새 요청이 오면 기존 조건을 덮어씁니다.
  • 부담 최소화 — 폴링 대신 전환 요청 시 구독하고 감지 즉시 해지합니다. 리스너는 FSM에 구현되어 있습니다.

05 AI 활용

Gemini · Claude Code CLI + Unity MCP를 사용했습니다. 어디까지 맡겼고 어디서 잘못 썼는지를 함께 남깁니다.

맡긴 범위

전체 코드 작성을 맡긴 것은 세 곳뿐입니다 — 커스텀 에디터 윈도우, Addressables 로드 · 세이브 · 덮어쓰기, 인벤토리 드래그. 나머지 게임 로직은 직접 작성했습니다.

주로 쓴 방식

클래스 · 함수 · 변수 이름을 묻는 일이 가장 잦았고, 그다음이 아키텍처 토론과 컨텍스트를 제공한 코드 리뷰였습니다. 작업 전에 예상되는 문제를 미리 확인하는 용도로도 썼습니다.

토론에 쓴 주제

async 내 Exception Swallowing의 원인, Saved By Batching이 0인 문제(SRP Batcher 동작 방식), Unity 라이프사이클에 따른 호출 순서 등입니다.

GIGO — 프롬프트가 결과를 갈랐다

[1] “이거 어떻게 구현해?” → 그 부분만 구현되어 기존 코드와 호환이 어렵고 일관성도 없었습니다.

[2] 사용 중인 코드를 함께 제공 → 컨텍스트 덕분에 더 나은 결과를 얻었습니다.

[3] QuestManager-plan.md를 읽히고 구현 요청 → 컨텍스트와 기획을 함께 주었을 때 가장 좋았습니다.

잘못 쓴 사례

Quest와 Scenario는 확장성을 충분히 고려해 설계했습니다. 그런데 AI에게 요청한 커스텀 에디터 윈도우가 하드코딩되면서, 두 시스템이 그 에디터에 의존하게 되어 확장성이 함께 죽었습니다.

시스템 설계를 아무리 열심히 해도 확장이 어려워 컨텐츠 추가가 까다로워졌습니다. 지금 돌아보면 AI를 잘못 사용한 예시입니다.

  • AI로 반드시 개발이 빨라지지는 않았습니다. 아키텍처에 관해 AI가 준 아이디어는 상당히 괜찮아서 QuestManager와 ScenarioManager에 많이 반영했지만, 그것을 이해하는 일은 결국 제 몫이라 그 지점에서 병목이 생겼습니다. AI가 기획 — 설계 — 구현 — 테스트까지 파이프라인 전체를 담당하지 않는 한 피해갈 수 없는 문제가 아닐까 생각합니다.
  • 과한 의존은 금물입니다. Exception Swallowing 문제를 물었을 때 잘못된 정보를 받은 적이 있습니다.

06 결과 평가

1개월이라는 기간에 비해 다소 높은 목표를 잡았고, 달성하지 못한 것들이 있습니다.

미달성
아이템 사용과 사운드는 우선순위에서 계속 밀려 결국 구현하지 못했습니다. 아이템 제작 · 분해 · 합성 · 강화는 메인 피처 중 가장 후순위로 밀렸고, 이를 포기하는 대신 기존 피처들의 테스트와 리팩토링에 집중했습니다. 스킬 가짓수도 부족합니다(마법사 4, 전사 2) — 전사는 근접 공격이라 애니메이션 에셋이 추가로 필요했고, 마법사는 투사체 종류로 늘릴 수 있어 요구량이 적었습니다.
목표 변경
무기 스왑을 캐릭터 스왑으로 바꿨습니다. 구현이 편하기도 했고, 요즘 오픈월드 RPG에서 무기 교체는 모델만 바꾸며 스킬은 캐릭터에 귀속되므로 이 방식이 더 적합하다고 판단했습니다.
초과 달성
계획에 없던 JobSystem을 보스 패턴에 적용했습니다. 크기가 작은 보스 Mesh를 대량으로 렌더링하는 데 사용했습니다.
배운 점
서로 다른 객체의 상태를 전달하는 방식(EventBus · delegate · 싱글턴 메서드)을 기능의 확장 가능성, 사건의 무게감과 빈도, 두 객체의 관계에 따라 고르게 되었습니다. 비동기 반환 타입(async void · async Task · async Awaitable)은 모르고 쓰다가 예외가 삼켜지는 일을 겪고서야 제대로 알게 됐습니다 (글로 정리했습니다 →). 계층적 FSM과 Player FSM에 UI FSM을 연동하는 방식, UI Layout 컴포넌트도 이때 익혔습니다.
아쉬운 점
NPC 구조를 처음부터 제대로 잡지 못해 모든 NPC가 QuestGiver가 되어버렸습니다. ScenarioManager는 설계 초기에 UI까지 함께 담당시켰는데 끝까지 관심사를 분리하지 않았습니다(QuestManager는 분리했습니다). QuestRewardHandler를 만들어 두고도 Exp 보상은 하드코딩했습니다 — ItemRewardHandler처럼 ExpRewardHandler를 구현하면 될 일이었습니다. Enemy는 여전히 StateMachineBehaviour 기반이라 Player와 코드가 일관되지 않습니다. 중반에 NavMeshAgent를 추가하며 이동 로직을 새로 짰고, 그 과정의 작은 버그(적이 사망 후에도 이동)가 방치됐습니다. 기획이 구체적이지 않아 데이터 구조도 복잡하고 불필요한 필드가 많습니다.
구조적 한계
Addressables를 데이터 컨테이너로만 썼습니다. 원래는 서버에 데이터를 올려두고 씬마다 필요한 것만 가져오려 했으나, 씬이 둘뿐이고 개별 데이터를 묶어두지 않아 거기까지 가지 못했습니다. 퀘스트 의존성(A 클리어 후 B 수행)은 각 QuestGiver가 자기 퀘스트를 따로 관리해 중앙 관리가 불가능합니다. 매니저가 특정 퀘스트의 클리어를 감지해 퀘스트 에셋을 갱신하는 구조 — 서버가 있다면 이 지점에서 반영 — 였다면 더 좋았을 것입니다.
총평
작동한다는 이유로 모르는 채 넘어간 것들 — async, 어드레서블 로더 등 — 을 깊이 이해할 필요가 있겠습니다. 시스템만 만들고 컨텐츠를 만들지 않아 설계에 지나치게 몰입한 감이 있습니다. 그래도 잘 된 점은, 일단 완성된 사이클로 게임이 돌아간다는 것입니다.
